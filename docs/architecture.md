# 系统逻辑

## 页面导航与资源

管理页面由 Go 模板服务端渲染。所有页面共用 `/assets/app.css`，侧栏切换时保留这份样式表和页面外壳，只替换侧栏内容、主内容及页面级弹窗。页面脚本先注册初始化函数；导航层在替换前中止上一页的 `AbortSignal` 并调用清理函数，在新 DOM 装入后再初始化当前页。事件监听、下拉菜单、弹窗和提示计时器都随页面卸载清理。表单提交和非侧栏链接仍使用浏览器原生导航；局部导航失败则回退到整页加载。

点击当前侧栏栏目会重新获取页面。管理员编辑已分配方案后，用户点击“我的密钥”即可按最新方案重新展示上游账号、可用时段和额度；页面不会定时轮询。

## 请求链路

```text
客户端 API Key → 附属服务 → 用户与方案校验 → 模型前缀选路 → 原 CPA → 上游账号
Linux DO OAuth2 → 附属服务会话              CPA 管理 API → 账号、额度、重置与模型信息
```

附属服务使用一套 `CPA_BASE_URL`，代理 API 请求使用 `CPA_API_KEY`，管理查询使用 `CPA_MANAGEMENT_KEY`（原 CPA 的 `management.secret-key` 明文）。它读取 CPA 的凭据列表、每个凭据的模型列表、全局模型、OAuth 模型别名及 AI 提供商配置，识别唯一、可路由的账号前缀；不会下载认证文件或保存上游 API Key。CPA 继续负责 OAuth 刷新。管理员在附属服务触发的凭据刷新会调用 CPA 管理接口。API 请求与用户页面共享账号快照（`CPA_ACCOUNT_CACHE_TTL`，默认 `15s`，范围 `0s`–`30m`，`0s` 关闭复用），并发查询合并为一次；失败不缓存，管理页与保存操作始终实时读取，因此 CPA 侧变更最多延迟一个缓存周期作用于 API 路由。快照在最后 1/5 有效期内被访问时会在后台提前刷新，请求继续使用尚未过期的快照，不会返回过期数据。CPA 对已加前缀的模型返回 `model_not_found`、`unknown provider for model`、`auth_not_found` 或 `auth_unavailable` 时，视为快照已过时：后台刷新快照（全局 30 秒最多一次），并尝试方案内下一账号。客户端无法借此放大管理请求，因为快照中不存在的模型在本地即被拒绝。较早发起的查询不会覆盖较新的快照。用户页面只展示账号前缀，重置表单使用按用户与方案签名的不透明引用，不暴露 CPA 凭据文件名。

客户端只传对外模型名。附属服务按已分配方案选取账号，在发往 CPA 的模型名前加该账号前缀；对客户端的 `/v1/models` 隐藏账号前缀并过滤 CPA 的 OAuth 模型别名，客户端直接请求别名会返回 404。价格列表和一键同步也不包含这些别名。多个账号按 CPA 优先级尝试，同级轮询。明确的会话 ID 在一小时内保持账号绑定，子代理沿用父会话；方案或账号配置变化后不沿用旧绑定。只有明确的额度不足或限流会触发下一账号。CPA 返回 `model_cooldown` 时，附属服务立即查询管理接口中该凭证的冷却范围：若 `scope=credential` 且为额度冷却，就按 CPA 的 `retry_at` 跳过该凭证的所有模型；否则仅按账号和当前对外模型记录 `reset_seconds` / `reset_time` 对应的恢复时间。模型级记录保存在 `usage.sqlite`，重启后仍生效；凭证级状态由 CPA 快照在重启后重新取得。管理查询失败时先按模型级冷却，避免继续撞击同一模型。方案内该模型的所有可用账号都冷却时直接返回本地 HTTP 429、`Retry-After` 和剩余时间，不再向 CPA 发起模型请求；到期自动放行。上游未提供有效恢复时间时临时冷却 30 秒。其他上游错误原样返回。

`POST /v1/responses` 启用 `X-OpenAI-Internal-Codex-Responses-Lite: true`（或等效的 `client_metadata.ws_request_header_x_openai_internal_codex_responses_lite`）时，上游要求 `reasoning.context=all_turns`。附属服务在审计、计费及实际转发前补齐这个字段；已有 `reasoning` 的其他字段保留。未启用 Lite 的请求不改写，其他端点不应用此规则。这样无需调整原 CPA 或客户端，但显式指定其他 context 的 Lite 请求会被规范为 `all_turns`。

管理员的“可用 CPA 账号”、用户的“上游额度”，以及仪表盘的已分配上游会标记正在冷却的凭证和北京时间恢复时刻。状态优先读取 CPA 凭据列表中的冷却快照：凭证级冷却表示整张凭证暂不可用，模型级 429/额度冷却显示为“部分模型冷却中”，不误判所有模型不可用。附属服务一收到 CPA 返回的 429，就在内存中标记对应凭证，并按 `Retry-After`（缺失时 30 秒）展示临时恢复时间，同时限频刷新 CPA 快照；经管理接口确认的凭证级冷却立即展示为“凭证冷却中”。普通 429 的临时状态只供页面展示，不参与硬路由限制。冷却到期后页面恢复原状态。

## 方案、时段与额度

每个方案至少有一个上游账号。每个账号的时间窗采用左闭右开 `[开始, 结束)`；未设边界表示该方向无限期。方案有效时段是各账号时间窗的合集，窗口间的空档禁止请求。时间轴展示账号可用、已占用、过去及已选择的时段；新设置的时间不能早于当前时间。相同账号不能在时间重叠的方案中重复使用，相邻时间窗可以交接。每个方案最多分配给一个用户。无方案、方案不在有效时段、账号冲突或用户禁用时，API Key 均不能请求。

每个方案可设置 RPM（默认 `0`，不限制）。附属服务在转发前按方案统计最近 60 秒已放行的 API 请求，所有分配给该方案的密钥共用上限；超限返回 HTTP 429 和 `Retry-After` 秒数。计数保存在单个附属服务进程内，重启时清零；部署时只运行一个附属服务实例。

额度预览按账号从 CPA 查询。Codex 的 `primary_window` 和 `secondary_window` 分别显示为“5 小时限额”和“周限额”，展示剩余百分比、北京时间恢复时刻及相对剩余时间。可手动重置的上限取自上游真实可用重置积分，方案设置的次数按账号在所有方案间共享预留；配置了次数时，页面按过期时间排序，从上游当前可用积分中展示最多与本方案剩余次数相同的过期时间。积分按账号共享，页面中的“第 N 次”表示本方案的可用次序，不表示与某个上游积分永久绑定；重置实际消耗由上游决定，页面刷新后重新读取最近可用的过期时间。若上游只返回可用数量而没有逐次过期时间，页面明确提示时间不可用。用户在自己的方案次数内可重置对应账号，操作有确认步骤。当前 Codex 和 Claude OAuth 支持真实重置积分；其他提供商若无额度或重置接口，相应信息不可用或上限为零。

可选 USD 使用额度在方案整个生命周期累计，编辑或重新分配不会清零。价格按对外模型分别保存为表达式，例如：

```text
len <= 272000 ? tier("0_272k", p * 2 + cr * 0.1 + cc * 2.5 + c * 10) : tier("272k_plus", p * 4 + cr * 0.2 + cc * 5 + c * 15)
```

`p` 是普通输入、`cr` 是缓存读取、`cc` 是缓存创建、`c` 是输出，单位均为百万 Token；`len` 是输入 Token 数。表达式是受限语法，不执行任意代码。一键同步仅匹配 CPA 对外模型且当前支持的表达式。有限额方案对未定价模型或未开放的接口在转发前拒绝。请求体中 `model` 以外的大小写变体（如 `MODEL`）一律拒绝，保证计价与转发使用同一模型。文本请求按请求体大小估算输入 Token，并用显式输出上限（未设置时取 256 Token）和模型表达式预扣费用；普通输入、缓存读、缓存写分别估价，取最高值。图片生成 `/v1/images/generations` 采用每张约 2–6 万输出 Token 的估计值，按尺寸、质量和 `n` 预扣；从 CPA 返回的 `usage.input_tokens`、`usage.output_tokens` 及缓存读取量结算，大段 base64 图片不会作为 Token 计入。Codex 搜索 `/v1/alpha/search` 至少按 4096 个输出 Token 预扣；有上游用量时按实际用量结算，否则按请求与响应字节数估算 Token 并标记估算，不因缺少用量字段暂停方案。预扣写入增量日志后才转发，方案剩余额度已扣除其他进行中请求的预扣；流式请求不持有方案全程锁。成功后按上游实际用量补扣或退回差额，失败时退回预扣。普通成功响应若缺少可用 Token 用量，按请求/响应字节数估算计费并暂停方案等待管理员检查；客户端取消流式响应时，优先用已收到的输出增量估算输出 Token（不把 SSE 帧和元数据算作输出），再结算预扣费用并在使用日志标记估算。无法识别增量时回退到已传输字节数。图片生成响应若缺少有效用量或中途中断，则按预扣额计费并暂停方案，避免将图片字节数当作 Token。管理员检查并重新保存方案可恢复。流式响应边转发边提取用量；实际费用可能超过预估，因此单个已开始请求仍可能让累计费用超过上限。服务异常退出时未结算的预扣保持扣费，避免漏计，需由管理员核查。

## 密钥和数据

Linux DO 用户 ID 是用户身份。管理员通过 `ADMIN_SUBJECTS` 指定，不在页面里授予管理员身份。API Key 由随机值生成，保存哈希及用 `cookie.key` 加密的副本，只有所属用户能从页面复制。轮换立即废止旧值。会话 Cookie 带会话版本号，退出登录会提升版本，使该用户所有已签发 Cookie 立即失效。API Key 只从 `Authorization: Bearer`、`X-API-Key` 或 `X-Goog-API-Key` 请求头读取，不接受 `?key=` 查询参数，避免写入访问日志。页面响应带 CSP（脚本按每次响应的 nonce 放行、`frame-ancestors 'none'`）和 `X-Frame-Options: DENY`，禁止被嵌入框架。请求体须在 60 秒内上传完，读完即解除限制，不影响长时间的流式响应。启动时会检查每把密钥都有加密副本，缺失时拒绝启动并报告密钥 ID。Cookie 密钥、用户、方案、价格、重置计数及密钥存于持久化 `/data`；用户资料和状态写入 `users.sqlite`，方案、价格和密钥写入 `store.json`；会话亲和绑定在单实例内存中，重启后重新选路。

用户资料保存在 `users.sqlite`，`store.json` 中的价格使用表达式，方案只保存逐账号时间窗；方案整体起止时间在读取时由账号时段推导，不单独持久化。审计配置使用 `audit.endpoints`。若存储被外部修改导致多用户分配或账号时段冲突，流量会被拒绝，需由管理员修正。

## 仪表盘与使用日志

仪表盘的最近 6 小时成功率、请求趋势及上游对比排除本地返回的 HTTP 429（包括 `model_cooldown` 与方案 RPM 限流）。这些请求仍写入使用日志，但不计入仪表盘请求数、失败数或成功率分母；CPA 返回的最终 429 计为失败。上游先返回 429、切换账号后成功的请求只按最终 2xx 计一次。其他状态码沿用原有统计口径。

附属服务将通过有效 API Key 的每次请求写入 `/data/usage.sqlite`。记录时间、用户 ID、请求当时的用户名快照、密钥 ID、方案、上游账号、模型、路径、最终 HTTP 状态、首字耗时（从请求进入附属服务到首次写出响应正文）与总耗时、输入/输出及缓存 Token、按当时模型价格计算的 USD 费用；不记录请求正文、响应正文或 API Key 明文。没有响应正文时，首字耗时显示为“—”。失败或在方案校验阶段被拒绝的请求也记录状态；无效 API Key 无法归属用户，因此不进入用户日志。

仪表盘按滚动的最近 6 小时展示请求总数、成功率、10 分钟吞吐、供应商流量、Token 与费用。“下一步”上方依次显示当前登录用户的方案概览和所有用户可见的公开分配列表。自己的方案包含状态、可用时段、RPM、累计 USD 额度和上游账号状态；公开列表列出所有用户的用户名、ID、方案、上游账号及各账号可用时段和状态，包括未分配用户。管理员切换到“全部用户”用量视图时，这两块分配信息不变。使用日志默认查询北京时间当天，可自选起止时间、模型、请求状态，以及用户（管理员）、API Key ID、上游账号 ID 和路径；页面以紧凑表格展示，支持单条详情、列显示控制、当前页 CSV 导出和分页。普通用户的查询始终按当前登录用户 ID 限制，管理员可查看全部或指定用户。没有配置价格或上游没有可用 Token 用量的成功请求可能显示费用为零；有限额方案的普通文本请求缺少最终用量时按估算计费并暂停后续请求，Codex 搜索则按请求与响应字节估算计费且不因此暂停方案，日志会标记估算。用户名在请求开始时写入日志，后续改名不会影响历史记录；费用与用量不会回填。

## 内容审计

管理员侧栏的“内容审计”位于“分流方案”下方。管理员在设置弹窗中启用审计，配置 1–5 个有顺序的审计接口、随机抽查比例、每个接口的决策超时、13 类风险概率阈值和失败回退关键词。每个接口独立配置名称、地址、模型名称和加密保存的 API Key；列表支持添加、删除和排序。启用时所有接口均须有 API Key，且至少配置一个回退关键词。默认完整地址为 `https://ai-gateway.vercel.sh/typesafe/v1/systemone`；所有接口都直接 POST 到管理员填写的完整地址，不再追加路径。现有配置中的 TypeSafe 根地址需在部署前一次性改为带 `/systemone` 的完整地址；`/v1/decisions` 保持原地址。默认模型为 `jev-latest`。CPA API Key 不会发送给审计服务。

抽查在转发前同步进行。可识别会话的首条请求必检，其余按设置的比例随机抽查；没有显式会话 ID 的 Chat 请求通过消息历史判断是否已有之前的用户轮次，无法判断的请求按首条处理。从原始请求体的 `messages`、`input`、`contents` 或 `prompt` 按顺序整理用户与助手的可见文本，含历史对话和当前用户消息；系统/开发者消息、工具调用与结果、结构化思考块、图片和音频均不进入审计文本。助手文本中的 `<think>` / `<analysis>` 块也会过滤。本轮模型回复尚未产生，不会进入这份请求上下文。文本受 16 MiB 请求体上限约束，不再仅截取最后一条用户消息。请求体采用 TypeSafe 决策格式：`model: 当前接口配置的模型名称`、13 个 `type: noul` 的 `questions`；`/systemone` 的 `state` 为整理后的对话文本，`/v1/decisions` 的 `state` 为包含 `conversation` 文本的对象。从响应 `answers.<类别>.noul` 读取 0–1 概率，与对应百分比阈值比较。单个接口超时、HTTP 错误或响应缺少有效答案时依次尝试下一个接口；全部失败时才对同一份上下文使用大小写不敏感的关键词匹配回退。

审计仅做记录，不拦截请求。每次实际抽查的元数据（含请求当时的用户名快照与用户 ID）写入 `/data/usage.sqlite` 的 `content_audit_records`；只有命中时保存整理后的对话上下文，未命中不保存正文。`audit_record_details` 保存成功接口名称、尝试接口数以及关联的使用日志 ID；使用日志写入完成后才更新关联。同一请求的多条审计记录指向同一条使用日志；日志写入失败时关联为空。数据库写入失败会记入服务日志，请求继续转发。最坏情况下审计等待时间约为接口数乘以单接口超时，备份和查看审计数据库时应按含有用户敏感文本处理。

CPA 返回的 OpenAI/Codex 结构化错误码 `cyber_policy`（兼容 `cyber_abuse`）也作为独立命中来源记录。附属服务观察最终发给客户端的 JSON 错误或 SSE `error` / `response.failed` 事件，按 `error.code` 或 `response.error.code` 判断；普通输出文本里出现相同单词不会命中。记录包含从该请求提取的对话上下文和“OpenAI 上游”来源，不包含触发标记的本轮模型回复；不改变 CPA 的 HTTP 状态、响应正文或流式传输，也不会因审计数据库写入失败而拦截请求。该来源不要求 TypeSafe 额外调用。
